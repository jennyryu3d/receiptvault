바이블 프로젝트 설계도

무엇으로 만들고, 에셋을 어디에 두고, AI를 어떻게 붙이고, 사람이 늘면 어떻게 나눌지. 한 문장으로 줄이면 — 지금 만들 수 있는 것부터 만든다.

웹 런타임 React + Three.js 정적 배포. PC 없이 지금 바로 가능.
시네마틱 프리렌더 영상 실시간 렌더 아님. 품질 상한이 없다.
에셋 저장 Git엔 레시피만 바이너리는 오브젝트 스토리지 + 해시.
AI 연동 어댑터로 추상화 제공자를 코드에 박지 않는다.

왜 언리얼이 아닌가

결정 · 되돌릴 수 있음

언리얼을 버리자는 게 아닙니다. 자리를 옮기자는 겁니다 — 웹 런타임이 아니라 렌더 도구로. 근거 셋을 순서대로 놓습니다.

① 언리얼은 웹으로 나가지 않는다

Epic이 UE4.23 이후 HTML5 익스포트 지원을 중단했고, UE5에는 공식 웹 빌드가 없습니다. "웹에서 구동"이 요구사항이면 언리얼은 런타임 후보에서 그냥 빠집니다.

② 11월까지 PC가 없다

언리얼·유니티·Godot 전부 데스크톱 에디터가 필요합니다. 태블릿으로는 불가능해요. 웹 스택은 제가 컨테이너에서 빌드하고 배포할 수 있고, 대표님은 브라우저로 확인만 하시면 됩니다. 지금 진행 가능한 유일한 선택지입니다.

③ 이 작품은 실시간 3D가 필요 없다

5컷은 12분 원테이크 시네마틱입니다. 그 품질을 실시간으로 뽑으려면 관객에게 고사양 GPU를 요구하게 되는데, 웹에서는 불가능에 가깝습니다. 프리렌더하면 품질 상한이 사라지고 저사양 기기에서도 돕니다.

엔진웹 배포PC 필요파일이 텍스트인가시네마틱 품질
언리얼 5없음필요아니오 — 블루프린트는 바이너리최상
유니티WebGL필요부분 — YAML+바이너리 혼재상

웹 네이티브정적 호스팅불필요예 — 전부 코드영상 품질에 달림

"파일이 텍스트인가"가 왜 중요한가

텍스트면 협업자가 — 사람이든 저든 — 직접 읽고 고치고 변경 이력을 볼 수 있습니다. 블루프린트처럼 바이너리면 에디터를 열 수 있는 사람만 손댈 수 있어요. 나중에 사람이 합류할 때 이 차이가 크게 벌어집니다.

이 결정을 다시 여는 조건

실시간 3D 인터랙션이 감정선에 꼭 필요한 컷이 생기면 Godot 4를 봅니다. 데스크톱·콘솔 출시가 목표에 들어오면 언리얼을 봅니다. 지금 웹으로 가도 그 문은 닫히지 않습니다.

에셋은 어디에 두는가

이 프로젝트의 척추

원칙 한 문장: 저장소에는 결과물을 다시 만들 수 있는 정보만 넣고, 결과물 자체는 오브젝트 스토리지에 두고 해시로 참조합니다.

컷 manifest — 파일 하나가 샷 하나

에셋에 관한 모든 진실이 여기 있습니다. seed와 model_version이 빠지면 두 번 다시 같은 걸 못 만듭니다. 

# shots/EP01/EP01_C05_S01.yaml
id: EP01_C05_S01
title: "절정 · 군중 와이드"
duration_sec: 14

look:
  world: past          # 색온도가 여기서 갈린다
  camera: "WIDE, 35mm, 고정"
  rule: "중앙은 성경 인물의 자리"

generation:
  provider: null       # 구현 시점에 실측 비교로 결정
  model: null
  model_version: null  # 모델이 업데이트되면 같은 시드도 달라진다
  seed: null           # 정해지면 절대 바꾸지 않는다
  prompt: |
    (아직 없음)
  refs:
    - assets/char/haran_sheet_v1.png

review:
  status: draft        # approved 없이는 조립에 못 들어간다
  reviewed_by: null

outputs: []            # sha256 + r2:// URI

생성 파이프라인

중요한 건 화살표가 아니라 검수 게이트와 거기서 뒤로 돌아가는 화살표입니다. AI 생성물은 사람이 안 보면 반드시 어긋납니다.

캐릭터 일관성 — AI 애니메이션이 무너지는 1번 이유

컷마다 얼굴이 달라지는 것. 대책 세 개를 동시에 겁니다. ① 인물별 레퍼런스 시트를 먼저 확정하고 저장소에 버전 박아 커밋 (이건 예외적으로 git에 들어갑니다 — 작고, 잘 안 바뀌고, 진실이라서) ② 인물별 베이스 시드를 정하고 컷마다 바꾸지 않기 ③ 위의 검수 게이트.

AI를 어떻게 붙이는가

MCP냐 API냐

먼저 오해 하나를 풀고 갑니다

MCP는 기능이 아니라 제가 도구를 부르는 규약입니다. 이미지·영상 서비스 대부분은 그냥 REST API고요. MCP 서버가 있으면 제가 대화 중에 직접 부를 수 있어 편하고, 없으면 파이프라인 스크립트가 REST로 부릅니다. 어느 쪽이든 결국 API 키가 필요하고, 결과물은 같습니다. 중요한 건 연결 방식이 아니라 그 위에 어댑터를 두는 것입니다.

어댑터 인터페이스를 먼저 정한다

이미지·영상 모델은 몇 달마다 바뀝니다. 특정 모델을 코드에 박으면 파이프라인이 그 모델과 함께 늙습니다. 인터페이스를 고정하고 제공자는 설정으로 갈아끼웁니다. 

// pipeline/adapters/<provider>.mjs — 제공자마다 이 셋만 구현
generateStill({ prompt, refs, seed, size })          → Asset
generateClip ({ prompt, firstFrame, seconds, seed }) → Asset
upscale      ({ asset, factor })                     → Asset

제공자 선정은 구현 시점에 같은 프롬프트를 실제로 돌려보고 정합니다. 지금 특정 모델 이름을 박아두면 그때 가서 틀립니다. 제가 여기서 생성물을 직접 보고 비교할 수 있으니, 그 비교 자체를 제가 돌릴 수 있어요.

정직하게 짚어둘 한계

텍스트→영상 모델은 12분 원테이크를 만들지 못합니다. 짧은 샷을 생성해 이어붙이는 방식이 됩니다. 즉 5컷의 원테이크 연출은 AI 생성이 아니라 언리얼/블렌더 렌더로 갈 가능성이 높습니다 — PC가 생긴 뒤에요. 1~4컷과 6컷은 AI 생성으로 충분히 시도해볼 만합니다.

키는 프록시 뒤에

키가 클라이언트에 내려가면 끝입니다. Cloudflare Worker가 키를 시크릿으로 들고, 앱과 파이프라인은 프록시를 호출합니다. ConvoTrans에서 이미 쓰고 계신 패턴이라 새로 배울 게 없어요. 사람이 늘어도 각자 키를 발급받을 필요가 없고, 사용량과 비용을 한 곳에서 막을 수 있고, 유출되면 시크릿만 교체하면 됩니다.

한 가지만 — 이 프로젝트는 처음부터 개인 키로 시작하세요. 개인 창작물에 회사 키가 섞이면 나중에 정리 비용이 큽니다.

사람이 늘었을 때

지금은 둘이지만 자리를 미리 비워둡니다. 중요한 건 조직도가 아니라 manifest의 어느 필드를 누가 책임지는지가 명확한 것입니다.

역할하는 일손대는 것
디렉터최종 판단, 감정선, 승인docs/ · manifest의 review
작가대사, 성경 본문 선정, 로그라인docs/ · shots의 title
비주얼프롬프트, 레퍼런스 시트, 색·구도assets/char/ · manifest의 generation
엔지니어 (저 포함)파이프라인, 웹 런타임, 배포pipeline/ · web/ · worker/

논의는 어디서 하든, 결정은 한 곳에

결정은 HANDOFF.md의 "설계 결정과 이유"에 한 줄로 남깁니다. 이유를 같이 적습니다. 6개월 뒤 "왜 이렇게 했지" 하고 되묻는 비용이 결정 자체보다 큽니다. 되돌린 결정도 남깁니다 — 다음 사람이 같은 걸 또 제안하는 걸 막아주거든요. receiptvault에서 이미 잘 하고 계신 방식입니다.

제가 할 수 있는 것과 없는 것

할 수 있습니다

  • 파이프라인·어댑터·웹 런타임 코드 전부
  • 키를 주시면 API 호출 실행 — 이 컨테이너에서 나갑니다
  • 생성된 이미지를 직접 보고 판단 — 생성→확인→재생성 루프를 제가 돕니다
  • 영상은 프레임을 뽑아 스틸로 확인
  • 웹 빌드, 브라우저로 실제 구동, 스크린샷, 배포
  • Figma 연동은 이미 붙어 있습니다 — 디자인 왕복 가능
  • 기획·연출 논의 (지금 하고 있는 것)

못 합니다

  • 언리얼·유니티·Godot 에디터 GUI 작업 — 뷰포트를 못 봅니다
  • 영상을 영상으로 감상 (프레임 단위로만)
  • 최종 미적 판단 — "이 컷 감동적인가"는 대표님 몫
  • GitHub 저장소 생성 — 권한 부족(403). 아래 참고
  • Canva 연동 — 인증이 안 되어 있습니다

지금

전제 확정 → 첫 에피소드 사건 확정 → 12컷

코드 한 줄도 필요 없습니다. 전제 3가지 중 하나라도 뒤집히면 6컷을 다시 쓰는 게 맞고, 그건 하루치입니다. 24컷에서 뒤집히면 한 달치예요.

12컷 이후

레퍼런스 시트 + 제공자 실측 비교

인물 얼굴을 먼저 고정합니다. 그다음 같은 프롬프트를 여러 제공자에 돌려 비교하고 어댑터 하나를 구현합니다. 이때 키가 필요합니다.

24컷 이후

파이프라인 + 웹 런타임

컷이 데이터가 되는 시점입니다. 생성 스크립트, 스토리지 연결, 영상 트랙 + 인터랙션 레이어를 짓습니다. 여기서 제 기여가 가장 커집니다.

PC 이후 · 11월~

언리얼/블렌더로 5컷 렌더

AI 생성으로 안 되는 12분 원테이크를 여기서 만듭니다. 그때쯤이면 나머지 다섯 컷이 이미 웹에서 돌고 있어야 합니다.

저장소 — 전용 저장소를 자동으로 만들려 했으나 GitHub 앱 권한(403)에 막혔습니다. bible-interactive 이름으로 빈 저장소를 하나 만들어주시면 전체 스캐폴드를 바로 올리겠습니다. 그때까지 작업물은 유실 방지용으로 임시 브랜치에 올려뒀습니다.
이 페이지 — 댓글을 달 수 있습니다. 고쳐서 같은 주소로 다시 올리니 링크는 바뀌지 않습니다.

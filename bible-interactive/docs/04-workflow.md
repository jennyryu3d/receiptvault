# 작업 흐름 — 사람이 늘었을 때

상태: 초안 (2026-09-01)

## 역할

지금은 둘(대표 + Claude)이지만, 늘어날 자리를 미리 비워둔다.

| 역할 | 하는 일 | 손대는 것 |
|---|---|---|
| **디렉터** | 최종 판단, 감정선, 승인 | `docs/`, manifest의 `review` |
| **작가** | 대사, 성경 본문 선정, 로그라인 | `docs/`, shots의 `title`·`logline` |
| **비주얼** | 프롬프트, 레퍼런스 시트, 색·구도 | `assets/char/`, manifest의 `generation` |
| **엔지니어 (Claude 포함)** | 파이프라인, 웹 런타임, 배포 | `pipeline/`, `web/`, `worker/` |

한 사람이 여러 역할을 겸해도 된다. 중요한 건 **manifest의 어느 필드를 누가
책임지는지가 명확한 것**이다.

## 한 컷이 완성되기까지

```
1. 디렉터   컷의 목적을 한 문장으로 → docs/
2. 작가     로그라인·대사 → shots/*.yaml
3. 비주얼   프롬프트·시드·레퍼런스 → shots/*.yaml (generation)
4. 파이프라인  생성 실행 → 스토리지 업로드
5. 디렉터   본다. 승인 or 반려 → review.status
6. (반려면 3으로)
7. 승인분만 조립 → 웹 빌드 → 배포
```

**5번을 건너뛰지 않는다.** AI 생성물은 사람이 안 보면 반드시 어긋난다.

## 새로 합류한 사람이 처음 할 일

1. `README.md` → `HANDOFF.md` 순서로 읽는다 (10분)
2. `docs/00-premise.md`의 전제 3가지를 이해한다 — 이게 작품의 헌법이다
3. 발행된 보드를 본다
4. `shots/`에서 자기 담당 컷의 manifest를 연다

저장소 clone은 수 MB다. 에셋은 필요한 것만 받는다.

## 결정을 남기는 법

**논의는 어디서 하든 상관없지만, 결정은 `HANDOFF.md`의 "설계 결정과 이유"에
한 줄로 남긴다.** 이유를 같이 적는다. 6개월 뒤에 "왜 이렇게 했지" 하고 되묻는
비용이 결정 자체보다 크다.

되돌린 결정도 남긴다. "넣었다가 뺐다"는 다음 사람이 같은 걸 또 제안하는 걸 막는다.
